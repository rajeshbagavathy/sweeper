Uncorrelated strategies

Runs against the top N rows exactly as filtered/sorted above. Two steps: 1) replay them and download each one's per-trade report from AlgoTest, reusing anything already cached by combo_id - 2) correlate whatever reports are on disk right now and rank a diversified basket, the best strategies that AREN'T just correlated clones of each other. Click a combo_id anywhere below to open its full detail and launch it in AlgoTest.

Off (default): step 1 above only fetches a report for a combo that doesn't already have one cached - fast, but a combo already downloaded (e.g. by auto-download during the original sweep) never gets touched again. On: every combo in the top N is replayed regardless of caching (except one downloaded in the last 24h, which is left alone - so an interrupted run can just be restarted instead of redoing everything), its start/end date window is rolled forward to end today instead of replaying the same window it was first discovered with (same length, just shifted - e.g. a year-long window stays a year, ending today), and its stored row is also updated with fresh metrics - including brokerage/taxes & charges (see config/selectors.yaml) - so a large candidate pool can be backfilled/kept current before building a basket off it. Each replay is a full backtest, so this is slower - a large top N can take a while.

Applies to step 1 above only (both plain and Force re-download) - a dedicated copy of the homepage's own "Parallel tabs" fields, kept separate on purpose. The homepage's fields only take effect through "Resume last run" there, and get silently restored to whatever a loaded execution's own saved value is on every page refresh - editing them was never actually reaching this download step at all. These fields are read fresh every time you click "1. Download reports" and are never overwritten by anything else on the page. Higher isn't always faster - too many concurrent real browser replays can starve each other for CPU/network and make the whole run look stuck with no progress; if that happens, lower this and try again.

A pick is added to the basket only if its correlation to every combo already picked stays below this. 0.5 is loose - a basket with several picks sitting at 0.4-0.49 is only barely diversified in practice. Lower it (e.g. 0.2-0.3) for a stricter, more genuinely uncorrelated (likely shorter) basket.

Portfolio: multi-session capital reuse

Runs ONE global diversification pass across every session together - same algorithm as Uncorrelated strategies above, so a pick is rejected if it's correlated with any higher-ranked pick anywhere in the day, not just within its own session - then splits the result into four time-of-day buckets and lot-sizes each within a real margin budget: a short-morning pick that frees part of the morning's margin, a midday pick that reuses it (never before that short-morning pick's own exit time), a long-morning pick held to early afternoon, and a separate full-margin afternoon pick. Each pick is lot-sized inversely to its own max drawdown - a bigger loser gets a smaller slice of its bucket's budget. Because this fits inside a real capital limit (the flat basket above implicitly assumes unlimited concurrent margin), its Reward:Risk will generally read lower than the flat basket's - that's the honest cost of it being a basket you could actually deploy, not a bug. Uses whichever file(s) are selected above; download reports for the sessions you want covered via Uncorrelated strategies first if a bucket comes back thin. Every field below (threshold, Top N, budgets, lots) is scoped to this basket only - separate from Uncorrelated strategies' own threshold above, and separate from CAS regime analysis's own copies of these same fields.

Short-morning and Midday lots are disabled and ignored in this mode - only Long-morning lots (now the "very long morning" budget) and Afternoon lots apply. Any entry before 12:00pm held to an exit at/after 2:00pm counts as one combined session, regardless of which of the regular buckets it would have fallen into (or fallen between) otherwise - see classify_very_long_morning_bucket in src/web/portfolio.py for the exact rule and why the regular buckets can't express this (an 11am-11:59am entry held past 2:15pm exit falls into no regular bucket at all today).

Off (default): the staleness check above only looks at the handful of combos that actually WON into this basket - fast, but fixing them can shift the ranking and surface a DIFFERENT stale runner-up next time you recompute, turning this into a repeated back-and-forth. On: the same check runs across every candidate still in contention (hundreds to a few thousand, not just the picks) - slower per click (it reads a lot more report files), but refreshing everything it flags in one pass means whoever wins next is already current, regardless of how the ranking moves afterward.

Lower the threshold (e.g. 0.2-0.3) for a stricter, more genuinely uncorrelated basket - same tradeoff as Uncorrelated strategies above. "Max lots per pick" (in lots, not %) stops one strategy from absorbing an entire bucket's budget even when it's the only clear winner - leave it blank for a loose default cap (40% of the bucket's own budget) instead of a fixed number. "Min lots per pick" stops a diversified-on-paper pick from being sized down to a token 1-lot amount that isn't a real position. If a bucket reports unallocated lots, that's the cap genuinely being too tight for how many picks are available - add more diversified picks to that session or raise the cap, don't expect it to disappear on its own. "Only since"/"Only until" restrict EVERYTHING - which combos even get shortlisted, not just the final numbers - to trades inside that window, so a combo that looks great over its whole downloaded history but has actually been flat or losing lately won't crowd out one that's specifically strong in the window you're asking about; leave either blank to use the full downloaded history on that side. "Flag picks with no data in the last N days" checks EACH FINAL PICK's own trade report against today's real date directly - different from (and catches more than) the correlation section's own "missing recent expiry data" warning, which only flags a candidate behind the rest of ITS OWN comparison pool and stays silent when the whole pool shares one old ceiling. There's no way to auto-detect a strategy's own trading frequency, so this is a plain day-count you set based on what you know about how often your picks should actually trade - a weekly strategy might need a looser number than a daily one. This staleness check is NOT applied to the sweep below - re-checking every grid point's own picks would mean re-reading trade reports once per combination, which is exactly the cost blowup the whole-pool checkbox above already warns about, just multiplied by however many combinations you're sweeping; use "Recompute basket" above to check staleness, then run the sweep once you're confident the data's current. "Only since"/"Only until" ARE reused by the sweep below (same date fields). Changing anything above and clicking Recompute re-runs everything, so feel free to reshuffle and compare - but don't chase the highest Reward:Risk number by trial and error across threshold/Top N: with only a few dozen overlapping trading days behind this, that number swings a lot between nearby settings and isn't a reliable thing to optimize against. Pick a threshold that looks genuinely uncorrelated in Uncorrelated strategies above, and a Top N wide enough that no bucket comes back empty; that's a better guide than the score.

Parameter sweep

Re-runs the basket above once per combination of the ranges below (threshold x Top N x Min lots x Max lots), using whatever's already downloaded - no new backtests, so it's fast even across a wide grid. This is the SAME "don't chase the highest Reward:Risk number" tradeoff as the warning above, just automated across many settings instead of one at a time - the table below shows every combination tried, on purpose, so you can see how much the number actually moves between neighbors rather than only seeing whichever one happened to score highest. A combination where Min lots exceeds Max lots is skipped rather than computed. Budgets and filters are reused from the fields above. Stopping partway through keeps every row already computed - Run sweep again with the same ranges resumes from there instead of starting over (only ranges/step values you change before running again get recomputed).

CAS regime analysis

This section's data is completely separate from everywhere else on this page.

Even if you already have thousands of matching reports downloaded via a regular sweep or Uncorrelated strategies, NONE of that is visible here - this section starts from zero for every exact [date range] you haven't explicitly downloaded for in step 1 below, every time, no matter how much data exists elsewhere on this page. If you just want CAS-style time-slicing of data you already have, use the regular Portfolio section's own "Diversify by CAS time-slice" checkbox instead - it reads from your existing downloads directly, no separate download needed.

A fully separate, isolated pathway for studying a genuine regime shift (e.g. CAS's introduction, after which decay reportedly concentrates in the last 15 minutes before expiry) - instead of filtering an already-downloaded full-year report down to a shorter window (which assumes AlgoTest's engine treats every day independently of the window it was asked to replay - not something we can verify), this replays each combo again with its start/end date PINNED to the exact period you specify below. Reports are written to their own folder (output/trade_reports_regime/, one subfolder per date range), never touching output/trade_reports/ or any result the rest of this page depends on - the basket-building logic itself is unchanged, just reading from a different place. Every field below (dates, threshold, Top N, budgets, lots) is scoped to this period only - separate from Uncorrelated strategies' own threshold above, and separate from Portfolio's own copies of these same fields.

1. Download reports for this period

Downloads the top N candidates from EACH of the 4 sessions separately (short-morning, long-morning, midday, afternoon) - not one flat "best overall" sort. A flat sort lets whichever session scores best historically crowd out the other three almost entirely, leaving them too thin to build a basket from below - this guarantees every session gets its own fair share of the download instead. Download at least as many per session as the highest Top N you'll ever try in the sweep below, or that session will still be candidate-starved. Replayed with start/end date pinned to the range below instead of each combo's originally-discovered window. Leave "To" blank for today. A report already on disk for this exact date range is left alone unless "Force re-download" is checked.

Every candidate's entry_time falls inside the same narrow CAS window, so the regular 4 day-of-time sessions would all collapse into one "Afternoon" bucket and "candidates per session" above would really mean "candidates overall", crowding out most of the window. This slices [Entry time from, Entry time to] above into N-minute bands and downloads the top N candidates from EACH band - set that range first (e.g. 15:14 to 15:30), then use the same slice width in step 2 below.

2. Multi-session basket (this period only)

Same bucketed multi-session algorithm as "Portfolio: multi-session capital reuse" above (build_portfolio itself is unchanged) - reading only from whatever was downloaded for the date range above. A candidate not yet downloaded there is excluded exactly like any undownloaded combo already is.

Every candidate's entry_time falls inside the same narrow CAS window, so the 4 day-of-time sessions above would all collapse into one "Afternoon" bucket and this basket would just be a flat top-N sort - not actually diversified across the window. This slices [Entry time from, Entry time to] above into N-minute bands instead and diversifies across those - set that range first (e.g. 15:14 to 15:30).
Overall lots is ONE shared cap for the WHOLE session, pooled across every diversified pick from every slice - not a separate budget per slice (CAS slices are all within the same few minutes and mostly exit around the same time, so their positions are concurrent, not sequential/reused like the regular day-sessions). Min/Max lots per pick above still bounds each individual pick, wherever its slice: the overall pool is divided across every pick (weighted toward lower-drawdown ones), clamped to Min/Max lots per pick - e.g. 4 picks, overall 20, min 3/max 5 comes out 5 each (fully deployed); raising overall to 30 with the same min/max still caps every pick at 5 (20 deployed, 10 reported unallocated) rather than exceeding the cap.
