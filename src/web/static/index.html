Re-entry on SL

Re-enter the leg after it's stopped out. Check any combination - each tried as a separate alternative, never combined on one combo (AlgoTest's own Re-entry on SL only holds one type per leg at a time, same as RE ASAP vs RE COST already worked).

"Re-entry count" only applies to RE ASAP/RE COST above - Lazy Leg has no count.

Lazy Leg: instead of re-entering the same strike, introduces a new, farther-OTM leg once the original is stopped out - smoothing the loss and catching a reversal. Every value below is derived from that same leg's own already-chosen settings - not something you configure separately, and not a new sweep dimension on its own (it's one more alternative within this same Re-entry on SL choice, same as RE ASAP/RE COST):

  • Strike: 2 strikes further OTM than the original (ATM→OTM2, OTM2→OTM4, ITM1→OTM1, ...), or half the premium for a premium-based leg.
  • Stop Loss % and Trailing SL: copied exactly from the original leg.
  • Momentum (reversal confirmation): underlying moves back 20pts (NIFTY) / 50pts (SENSEX) before the lazy leg fires - down for a CE original, up for a PE original.
Only applies when the original leg's own Stop Loss is percentage-based (not "Underlying %") and between 25%-60% - outside that range, or with no leg-level Stop Loss at all, that leg simply gets no lazy leg for that combo (it falls back to no re-entry, same as if Lazy Leg had never been checked). Only NIFTY and SENSEX have a confirmed momentum threshold - other instruments are not eligible yet.

Result settings

Applied to every result before scraping metrics. Brokerage and Taxes & charges are always turned on to match how you check results manually.

The brokerage rate is a one-time AlgoTest setting that persists for the whole sweep session, so it's only set once (on the first combo), not re-applied per combo.

Downloads a combo's trade report right after its backtest completes, if it already looks good enough - avoiding a full second replay later (login + fill + wait) just to fetch the report for something Correlate would have wanted anyway. Saved to the same combo_id-keyed cache Correlate checks, so it's simply already there when you get to it.

Only matters when more than one DTE is checked above. Off (default): one result row per combo, reflecting every checked DTE combined - today's behavior, unchanged. On: re-filters that SAME already-completed backtest to one DTE at a time (no extra "Start Backtest") and captures each as its own row - e.g. checking DTE 0, 1, 2 always writes three independently-rankable rows for the combo instead of one blended result, regardless of how good or bad any of them (or the blend) turns out to be. Each variant gets its own id (combo_id + "_dte" + N) so it shows up in Correlate/Portfolio like any other combo - nothing about how an ordinary combo's id is computed changes. The trade report FILE for a variant is still only auto-downloaded if that variant's own numbers clear the "Auto-download" quality bar above (same rule as the combined case, just judged per-DTE instead of on the blend) - the row itself, which is what you need to compare DTEs against each other, is never gated on that.

A combo's id is a hash of its ENTIRE definition, including start/end date - an identical strategy re-swept with a different end date (e.g. a trailing "today") gets a completely different id, silently fragmenting its own history instead of extending it. On (default): a combo whose underlying strategy already has a record in output/combo_registry.csv under a different id is not replayed - it's captured into a pending queue instead (see the panel below), for Force re-download to bring current against its EXISTING id. Off: every combo is always replayed as if new, no registry lookup at all - today's original behavior, for a deliberate full rediscovery pass.

A combo must also be profitable (total P&L > 0) - that gate is always on, not configurable. Return/MaxDD (not reward:risk or win rate) is the quality bar on top of that, since those two trade off against each other - gating on either alone would systematically exclude a whole category of good strategies.

Run options

Parallel tabs run independent combos concurrently in the same browser session (AlgoTest allows up to 15 concurrent strategy runs per account). 1 = sequential (today's behavior). Headless is effectively required above a few tabs. Accounts 2/3 (0 = disabled) use ALGOTEST_EMAIL_2/PASSWORD_2 and ALGOTEST_EMAIL_3/PASSWORD_3 from .env, each with its own separate browser profile - confirmed live that AlgoTest throttles concurrency per account, not per machine, so splitting workers across accounts gives real additional throughput instead of competing for one budget. Combos are still never run twice - each one goes to exactly one worker on one account. Total tabs across all accounts are real browser processes on this machine - watch memory (not just CPU) before pushing the total much past what you've already tested.

Filter by Instrument

One pill per index actually run (e.g. NIFTY vs BANKNIFTY) - now that one master CSV can hold results for several indices, this narrows everything below to a single one. Applied before every other filter.

"Best of Best" blends Return/MaxDD (overall equity-curve risk-adjusted return - the strongest single signal for whether the drawdown is survivable) with Reward:Risk ratio (per-trade payoff shape - a check that the return isn't just one lucky trade). Both are normalized before blending. 65% RMDD / 35% Reward:Risk is a starting suggestion, not a rule - raise the RMDD weight to prioritize surviving drawdown, lower it to prioritize consistent per-trade payoff.

Looking for the best strategies that AREN'T just correlated clones of each other? Head to Analyze all results → - filter/sort there, then use "Uncorrelated strategies" below its results table.
